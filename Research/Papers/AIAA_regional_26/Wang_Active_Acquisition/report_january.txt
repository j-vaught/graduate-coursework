Short Summary: The M300C setup is completed, improved performance by using MJPEG and splitting YOLOv8 across GPU and DLA and built a GUI to easily run the system and adjust tracking, zoom, and movement settings.
Summary: A mount for the two FLIR M300C cameras was completed, along with updates to wiring for reliable power distribution for both cameras. Camera latency improved considerably compared to the previous single slew to cue FLIR camera setup, and performance was further optimized by running one model on the GPU and the other on the DLA instead of relying solely on the GPU. A GUI has been created and is currently under development to simplify system setup and make adjusting camera settings easier.

Hardware Setup
The FLIR Cameras are mounted on the same platform and pointed in the same direction. Both cameras are then powered by the same 12.8-volt battery. To connect to the orin, they are connected to the network card directly. Initially, connecting to the POE enabled network card was considered unsafe, but further research showed the card used IEEE 802.3at POE detection to verify whether a device is POE capable, meaning non-POE devices can be connected safely. Software Configuration
The software for the current dual-camera setup integrated components from the original single-camera system and the subsequent dual-camera gimbal setup. As for how the overall system works, it works similarly to how the gimbal dual-camera system. There is one camera that remains stationary and one camera that will have full PTZ movement for object tracking. The stationary camera will have a lower optical zoom in comparison to the PTZ camera. Due to the smaller field of view, the PTZ camera may not detect objects visible to the stationary wider-angle camera. As a result, the wide-angle camera serves as the detection lead, calculating the initial coordinates required to ‘cue’ the PTZ camera. This allows the target to be brought within the PTZ camera’s FOV, at which point the PTZ unit will begin tracking from its own perspective. If the PTZ for some reason loses detection, the program will then switch back to tracking from the stationary camera perspective. Once the PTZ regain detection on the object, the program will switch back to tracking from its perspective. The overall operations of the system described above is depicted in Figure 4. As for the overall structure of the current software, it is depicted in Figure 5. The program is separated into a 3-layer structure. In order from L1 to L3, each of the layers are the graphic user interface layer, video processing layer, and tracking layer.

Figure 4 Dual-camera system operations illustration


Figure 5 Software structure for dual-camera slew-to-cue
L1 includes a GUI built using Kivy and a streamer thread that provides video streams of both camera feeds to it. GUI allows a user to easily operate the dual camera system and adjust settings on the system without interacting with the codebase itself. These settings include PTZ camera’s zoom, movement speed, tracking mode, and PID values used to smooth and stabilize camera movement during tracking. An image of the GUI window can be seen in Figure 6
L2 includes each camera’s respective threads used to produce the live feed seen in the user interface in L1. For each camera, this includes a capture thread to obtain live feed from the cameras, a YOLO processing thread to process individual frames for object detection, and a thread to draw boxes around the detected object. While tracking is disabled, the system only displays this processed feed with detection overlays. However, when tracking mode is switched to auto, detection coordinates from each camera’s respective YOLO threads are then transmitted to L3, where they will be used to drive the system’s tracking logic and camera movement.
When tracking mode of the GUI gets switched to auto, L3 manages the system’s movement through a two-phase process of acquisition and active tracking as described previously with Figure 4. This tracking architecture is designed to transition the system from a wide area search using the stationary camera to a high precision lock on a target using the PTZ camera. The way the modules relating to tracking are structured is similar to the architecture of the software used in the singular FLIR Camera system. The structural similarity allows the current program to reuse the established camera control and communication modules, including the HTTP protocols required for hardware commands. This layer manages the transition from initial target acquisition to high-precision tracking, ensuring that the PTZ camera remains locked on the desired object.

Figure 6 Kivy GUI of the current slew-to-cue software
The first phase, acquisition, begins when the stationary camera detects an object and sends the pixel coordinates of that object to the tracking process for conversion to azimuth and elevation degree values. These values are directed to the PTZ camera to roughly point towards the target location based on the stationary camera’s wide-field perspective. The second phase, active tracking, is initiated once the PTZ camera detects the target within its own field of view. This is when tracking becomes solely driven by the PTZ camera’s feed. Simultaneously, a real-time calculation of the object’s size relative to the screen percentage is performed. This adjusts the optical zoom to main the target with a specific percentage range relative to the screen size of the camera view. To ensure movements are fluid and precise, the azimuth and elevation coordinates of the camera from either phase are passed through a PID controller. The resulting azimuth and elevation commands are sent via HTTP commands to the PTZ Camera for camera control. Optimization
	Optimizations needed to be made when working on this current version of the system. From previous versions of the system, several challenges about certain aspects of the current version were made apparent. One of them is the noticeable latency of the real time video feeds coming from the FLIR M300C and the other was the massive drop in frame when running two instances of YOLO of any version. To solve the latency issue, it was mainly changing the codec of the FLIR camera streams from H.264 to MJPEG. 
For H.264, the frame decoding process involves dependency frames which forces buffering multiple frames before outputting any single frame. This buffering adds 2-4 frames of latency before YOLO even receives the image. This combined with the YOLO processing time and possible frame drops when streaming over ethernet added to the perceived latency of the final resulting video stream of the previous slew to cue system involving the FLIR. Due to the latency, tracking commands for the camera needed to have a delay before you could send a subsequent one or else the camera would overshoot on targets especially with faster moving ones. With a PID controller, the delay between commands was less, and the tracking was overall smoother but made the tracking less responsive in comparison and could only track targets moving below a certain perceived speed within its field of view
MJPEG encodes each frame independently as a JPEG, allowing immediate decoding with no frame dependencies leading to immediate output. Adjusting to this encoder made video feeds, even with YOLO processing, seem nearly instant. This made it perfect for real-time tracking applications such as this one. A PID Controller is still needed even with the improved frame latency, or else the camera will overshoot and cause unintended jerky movement. With MJPEG codec combined with PID Controller, tracking is now even more responsive and smoother even with objects moving at a faster perceived speed within the camera field of view.
In regard to the frame drops when running two instances of YOLO, it’s mostly because both are competing for the same GPU resources. Since they share the same hardware, the system uses ‘time-slicing’ to rapidly switch between the two instances. This constant context switching creates processing overhead, forcing the models to take turns rather than running truly in parallel, which results in significant latency and dropped frames. To resolve this resource competition issue on the GPU, the two cameras are now split between the Orin’s independent hardware engines. The stationary camera runs on the GPU, while the PTZ camera model is offloaded to the DLA. This strategy leverages the GPU’s high-performance computer for the stationary camera’s wide-angle view, where detecting small, distant objects requires more complex feature extraction. The PTZ camera zooms in on targets, making them larger and easier for the DLA’s specialized, lower-power and therefore less precise logic to process.

Each camera utilizes a specific model size optimized for its respective engine. The stationary camera runs YOLOv11s on the GPU to maintain high detection accuracy for distant objects, while the PTZ camera runs the ultra-lightweight YOLOv11n on the DLA to prioritize the high frame rates and minimal latency essential for active tracking. YOLOv8 was selected for this project initially because it currently has the most well documented for Jetson Orin deployment. This vast documentation provided the most necessary examples to successfully implement a dual-hardware (GPU+DLA) configuration for the first time, ensuring that both models could run in true parallel without resource contention. Currently, YOLOv11 is being used as it has significant performance advantages over its predecessor especially during training. It’s implementation on Jetson Orin is also pretty similar to its predecessor allowing for quick transitions from one model to another. Larger YOLO model sizes utilizing larger input sizes are also being investigated for better distant object detection for the stationary camera.
AAIA Conference Paper
Currently, I am writing a paper for the AAIA Conference with another Master Research Assistant Jacob Vaught about the application of this system for small object classification. Initially, the object that this system was initially targeted to classify was maritime objects such as boats and buoys. However, the subject classification needed to be changed to aircraft to better fit the conference’s focus. The default YOLOv8 model does have an ‘airplane’ as a target class. When performing tests with the ‘airplane’ target class selected on the default model, it seems that the below a certain size, the model has a hard time tracking. This effectively renders the stationary camera useless for long-range acquisition, as it cannot generate the initial coordinates required to trigger Phase 1 needed to point the PTZ camera toward the target. This can be seen in the screenshot of the Kivy GUI window in Figure 6.
As a result, YOLOv8 needed to be trained on datasets that mainly consist of drone and plane images taken from the ground up in RGB format. The datasets that were eventually chosen for accurate drone detection was the drone detection dataset  and for accurate plane detection FGVC  was chosen. These YOLOv8 models trained on these datasets have yet to be tested with the system. Future benchmarks with the models will be focused on comparing the mean Average Precision against the default YOLOv8 classes to ensure tracking accuracy is improved. The benchmarks will be done on a test dataset with long distance aircraft appearing and close distance aircraft appearing. Then real-world testing will be done to validate distant aircraft that can be detected by the stationary camera and the PTZ camera center and zooms on the detected aircraft as intended.
